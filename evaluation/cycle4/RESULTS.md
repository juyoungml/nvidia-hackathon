# Cycle 4: 실제 조사 루프와 시점별 근거

2026-09-28. **고정 비교에서 Ultra 경로는 2/4, 제한된 Claude Code + Sonnet 5 경로는 4/4가 출력 계약과 참조 검사를 통과했다.** 특화 하네스의 우위를 입증하지 못했다. 이 비율은 진단 정확도나 현장 유용성이 아니다.

## 구현과 비교 조건

저장된 답변을 다시 구성하는 시험에서 벗어나, 실제 도구 조회 → 점검안 생성 → 원본 사실 연결을 실행했다. 모델은 점검과 근거 ID를 선택하고, 프로그램이 해당 근거의 합집합으로 관측 목록을 구성한다. 별도 관측 목록과 점검 참조가 어긋나는 중복 작성 문제를 줄였다.

Ultra에는 시점별 공급온도·설정값 조회와 편차 구간 도구를 연결했다. 2°C는 설명용 편차 기준이며 고장 판정 기준이 아니다. 기준선에도 같은 원자료·사실 ID·시점별 자료와 출력 스키마를 제공했다. Claude Code는 Read/Glob/Grep 및 native StructuredOutput만 허용한 경로다. 무제한 코딩 에이전트와의 비교는 아니다.

[프로토콜](PROTOCOL.md), [선정 사례](cases.json), [입력 manifest](manifest.json)를 추론 전에 고정했다. 개발 사례 52·3과 처음 평가하는 별도 설비 사례 29·47을 각 경로에서 한 번씩 실행했다. 모델과 하네스가 동시에 달라 하네스만의 효과는 분리할 수 없다.

개발 사례는 Ultra 1/2, Sonnet 2/2; 신규 사례도 각각 1/2, 2/2다. 실패한 실행의 짧은 시간을 속도 향상으로 해석하지 않는다. 전체 측정값과 원본 trace 경로·해시는 [results.json](results.json)에 있다.

Ultra의 두 실패는 서로 다른 유효 조회를 여섯 번 수행한 뒤 종료 신호를 보낼 차례가 남지 않은 제어 문제였다. 잘못된 최종 답변으로 분류하지 않는다. 생성된 최종 계획에서는 이전 주기의 관측 목록·근거 참조 불일치가 재발하지 않았다. 이것만으로 점검 내용이 더 좋아졌다고 판단할 수는 없다.

Ultra는 네 사례 모두 시간 자료 도구를 읽었다. Sonnet도 fact catalog를 통해 같은 시간 자료에 접근했으며 네 사례 중 세 사례에서 시간 자료의 사실을 선택했다. 별도 temporal 파일을 열지 않았다고 시간 자료를 보지 않았다고 평가하면 안 된다.

## 내용 검수와 기록의 한계

사례 3의 Ultra 점검 이유는 “11:00부터 설정값이 내려갔다”고 설명하지만, 연결한 근거에는 해당 11:00 값이 없다. 시간 구간의 일부가 근거에 연결되지 않은 것이다. [사후 시간 인용 검수](temporal-review.json)는 이 항목을 사람의 검토 대상으로 표시한다. 시간 문자열 검사는 의미적 함의나 인과관계를 판정하지 않으며, 경고가 없다는 사실도 정확성을 보증하지 않는다.

초기 실행 기록에는 요청 객체의 messages 목록을 복사하지 않아, 이전 요청 스냅샷에도 이후 문맥이 포함되는 로깅 오류가 있었다. 따라서 원래 trace의 요청별 입력 prefix를 정확한 전송 기록으로 사용하면 안 된다. 응답·도구 실행 기록·시간은 보존되어 있다. 원본은 수정하지 않고, 이후 실행부터 전송 직전 깊은 복사를 적용했다.

독립 전문가의 맹검 평가, 원인 식별 성공률, 작업 시간 절감은 측정하지 않았다. 새 사례도 동일 공개 지역난방 자료의 난방 부족 신고이므로 발전소 전체 고장 유형으로 일반화할 수 없다.

## 비교 종료 후 개발 수정 — 주 결과에 합산하지 않음

선택 정책 `bounded_finalize_v2`를 추가했다. 유효 조회 여섯 번을 마치고 종료 신호만 남지 않은 경우, 기존 총 예산인 계획 요청 6회 + 최종 생성 1회 안에서 최종 단계로 넘긴다. `planning_cap_handoff`와 `investigation_budget_exhausted=true`를 기록하고 검토 안내를 붙인다. 에이전트가 충분한 근거를 모았다고 선언한 것으로 취급하지 않는다. 잘못된 조회·시점 경계 위반·공급자 오류에는 적용하지 않는다.

[기존 사례 52의 별도 개발 실행](development/handoff-v2-case52.json)은 같은 자료에서 27.811초, 관측 12개·점검 3개로 참조 검사를 통과했다. 한 사례의 수정 확인이며, 원래 결과 2/4를 바꾸거나 새 정책의 일반 성능으로 발표하지 않는다. 고정 비교의 기본 정책 `explicit_finish_v1`도 보존했다.

## 다음 검증과 재현

1. 변경 정책을 명시해 새 실험 프로토콜을 고정하고 아직 보지 않은 사례에서 재검증한다. 이번 신규 사례 29·47은 이후 개발 자료로 취급한다.
2. 우선 점검의 타당성과 문장별 근거 연결을 방법 이름을 가리고 검토한다. 시간 인용 경고를 없애는 것과 조사 품질 개선을 구분한다.
3. 같은 모델에서 일반 파일 조회와 도메인 도구를 비교해야 하네스 자체의 기여를 분리할 수 있다. NVIDIA 기술은 실제 조회·생성 역할과 검증된 경계로 설명한다.

고정 주기 재실행은 아래 명령을 사용할 수 있다. 새 출력 경로와 그 상위 디렉터리에 기존 결과가 없어야 하며, 재실행은 최초 평가를 대체하지 않는다. NVIDIA 키와 Claude 인증이 필요하고 API 비용이 발생한다. 이후 로깅 수정 때문에 요청 기록은 최초 trace와 다르다.

```sh
uv run python -m evaluation.run_live_cycle \
  --expected-protocol-sha256 efc2812ccdc5e8252534cce64f6b255b71f5b124ca81206cb068e3910a8d2cef \
  --output-dir evaluation/cycle4-rerun/traces
```

검증: Ruff 검사·포맷, Vulture(min-confidence 80), unittest 98개 통과. 이번 변경은 Markdown과 조사·평가 코드에 한정하며 기존 웹 재생·PDF·영상은 이전 실행의 스냅샷이다.
