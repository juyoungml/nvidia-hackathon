# System 2 vs Claude Code + Sonnet 5 — 비교 결과

2026-09-28 · protocol v2 · 각 구성/사건당 1회 · 저자 검토

## 결론

**이번 설정에서 ‘발전소 특화 조사 하네스가 일반 코딩 에이전트보다 낫다’는 가설은 지지되지 않았다.**

공통 출력 계약에 따라 표시 가능한 답변은 Ultra 기반 System 2가 5건 중 2건, Claude Code + Sonnet 5가 5건 중 5건이었다. Ultra의 세 보류는 관측 사실 선택 개수 제한(최대 12개) 초과 때문이다. 이것은 출력 제어의 실패이며, 그 세 답변의 모든 사실이 틀렸다는 뜻이 아니다. 의미적 정확도·현장 유용성·식별 시간의 승패는 이 수치로 판단하지 않는다.

## 무엇을 비교했는가

- **D / 도메인 조사:** Nemotron Ultra, 공개 replay 전용 읽기 도구 4개, 제한된 사실·점검 카탈로그, 공통 출력 검증.
- **G / 범용 파일 조사:** Claude Code 2.1.283 + 정확한 모델 `claude-sonnet-5`, 격리된 공개 파일 디렉터리에서 Read/Glob/Grep만 사용, 같은 카탈로그와 출력 검증.
- 사건별 같은 질문·허용 자료·스키마를 사용했다. 파일·코퍼스 해시 일치 검사를 통과했다.
- 범용 에이전트의 shell·웹·쓰기 기능은 비활성화했다. 따라서 제한 없는 Claude Code 전체 능력과의 비교가 아니라 **동일한 공개 자료를 읽는 제한된 파일 조사 구성**과의 비교다.
- 모델과 하네스가 함께 달라진 전체 시스템 비교다. 차이를 하네스만의 인과 효과로 해석할 수 없다. 같은 Sonnet 5에 도메인 MCP 도구를 제공하는 별도 보조 시도는 했지만, 실제 도구 호출을 확인하지 못해 유효한 동일 모델 대조군은 확보하지 못했다. packet-only 비교는 실행하지 않았다.
- 점검안은 사전 정의한 유형 중 선택하고 이유를 작성한다. 무제한 진단 또는 새로운 점검 계획 창작의 평가가 아니다.

설계·사전 조건: [프로토콜](../SYSTEM2_PROTOCOL.md) · [사건 manifest](../system2-case-manifest.json)

D는 모두 4개 도구를 호출했다. G는 9–10개 파일 도구 요청을 기록했고 모두 12개 사실·3개 점검을 선택했다. 도구 호출/파일 요청 수는 서로 동일한 작업 단위가 아니며 적을수록 좋은 지표가 아니다. 모두 자료를 읽었다는 자체 검사도 의미적 이해를 증명하지 않는다. 특히 G의 파일 접근 추적은 요청 경로를 기반으로 하므로, 각 파일의 성공적 읽기를 독립적으로 감사한 결과로 확대하지 않는다.

전체 시간은 관측된 벽시계 시간이다. D의 보류 답변을 포함해 평균을 내고 이를 속도 우위로 주장하지 않는다. D의 모델 요청 시간은 각각 34.35, 20.20, 36.76, 33.15, 23.19초이며 반올림 차이가 있다. G에는 CLI 시작·파일 도구·에이전트 루프 시간이 포함된다. 계산 자원과 추론 예산이 같지 않으며 현장 식별 시간을 측정하지 않았다.

G의 CLI가 보고한 `total_cost_usd` 합계는 v2 5회에 약 USD 0.4991이다. 실제 계정 청구액으로 간주하지 않는다. D의 비교 가능한 청구 비용을 확보하지 않았으므로 비용 우위를 판단하지 않는다. v1·가용성 점검 비용은 이 합계에 포함하지 않았다.

## 내용 검토: 형식 통과와 별개인 문제

모델 이름을 가린 [응답 쌍](v2-review/blind-review.md)으로 내용을 먼저 읽고 검토했다. 작성자는 이미 실험의 집계 결과와 개발 맥락을 알고 있으므로 **독립 전문가의 맹검 평가가 아니다.** 사후 진단 파일은 읽지 않았다. 아래는 전체 정확도 점수가 아니라 구체적인 검토 사항이다.

- **사건 52:** 표시된 두 답변 모두 공급온도 추종과 고객 실내 열 전달의 차이를 구분하고, 실내 상태·2차측 유량·이전 조치 확인을 제안한다. 큰 질적 차이를 확정할 근거는 없다. 한 답변은 밸브·펌프·공기잠김을 예로 추가하는데, 그런 고장이 관측됐다는 근거는 없다. 제안 이유와 관측 사실을 구분해야 한다.
- **사건 3:** 두 답변 모두 공급·설정값 하강과 편차를 활용해 실내·유량·제어 이력 확인을 제안한다. 공급온도 하강만으로 유량 손실이 원인일 가능성을 특정할 수 없고, 최대 편차가 하강과 같은 시점인지도 집계값만으로 알 수 없다. 시점별 조회가 추가로 필요하다.
- **사건 63:** 표시된 답변의 유량 확인 이유에는 유량이 감소한다는 표현이 있으나, 그 이유에 연결된 선택 사실은 마지막 값 하나다. 전체 원자료에 다른 값이 있더라도 **표시된 주장–근거 연결 자체는 추세를 지지하기에 부족하다.** 참조 ID 검사를 통과해도 이러한 오류가 남는다.
- **보류된 세 답변:** 공통 검증기에서 개수 초과로 표시를 차단했다. 이것을 내용 오류 세 건으로 계산하지 않았으며, 사후에 항목을 잘라 통과 처리하지 않았다. 원문은 그대로 보존했다.

## v1은 순위 결과로 사용하지 않는다

첫 버전에는 검증기의 일부 개수·길이·참조 규칙이 공통 입력에 충분히 공개되지 않은 문제가 있었다. Claude의 JSON code fence도 즉시 거부됐고, D의 세 사례는 도구를 읽지 않은 채 신고만으로 답했다. 이 결과를 유불리 점수로 사용하지 않았다.

v2 실행 전에 규칙을 모두 공개하고 단일 바깥 코드 블록만 양쪽에 동일하게 제거하도록 했다. 자료의 미조회 상태와 실제 결측도 분리했다. 이후 다섯 사건의 응답을 보고 프롬프트·카탈로그·검증 조건을 바꾸지 않았다. 원래 실패는 [v1-pilot](v1-pilot/)에 남아 있다.

## 이번에 구현한 개선과 남은 것

**구현:** 관측 사실은 원본 값·필드·시간·출처를 가진 불변 fact ID에서 선택하고 프로그램이 원문에 맞게 표시한다. 없는 ID, 참조 관계 오류, 계약 위반은 보류하며 원래 응답을 보존한다. 모델이 작성한 점검 이유는 별도 표시한다.

**남은 것:** 최종 형식 제약을 안정적으로 지키게 하는 생성 방식, 이유 문장 전체의 주장–근거 타당성, 시점별 추가 조회, 점검 우선순위의 독립 검토. Nano reranker와 선제 감시는 이번 실험에 넣지 않았다.

다음 수정은 제한을 사후 완화해 이번 통과 건수를 올리는 방식이 아니다. 출력 형식을 API 수준에서 제약하는 방법의 지원 여부와, 이유가 요구하는 관측 구간을 실제로 조회하는 기능을 각각 검토해야 한다. 새로운 프로토콜과 별도 시험에서 판단한다.

## 보조 시도: 모델을 Sonnet 5로 고정

주 비교 종료 후 사례 52 한 건에서 같은 Sonnet 5에 공개 도메인 도구만 제공하는 MCP 구성을 시도했다. 같은 코퍼스 해시였지만 실제 MCP 호출은 0회였고, 신고 사실만으로 답해 완전성 검사에서 보류됐다. 로컬 MCP 서버의 handshake/결과 시험은 통과했으나 Claude Code의 제한된 설정에서 도구가 유효하게 사용되는 비교 경로를 입증하지 못했다. safe mode의 영향은 가능한 원인이며, 이 실행만으로 원인을 확정하지 않는다.

관측 시간 9.047초, CLI cost metric 약 USD0.01362. 접근 제한을 풀거나 재시도해서 성공 실행을 고르지 않았다. [원문](posthoc/sonnet-domain-tools-52.json)은 설정·도구 사용 검증 실패로 보존하며, Sonnet의 조사 품질 또는 v2 통과율에 합산하지 않는다. 동일 모델의 유효한 하네스 비교는 여전히 남아 있다.
