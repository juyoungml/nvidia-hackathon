# Cycle 3 결과 — 오류를 고치는 것과 근거 관계를 보존하는 것은 다르다

2026-09-28 · 각 사건/구성 1회 · 주 비교와 별도 개발 시험을 분리함

## 이번 결정

**단순한 한 번의 수정 요청은 일부 출력을 복구했지만 Sonnet 대비 우위를 만들지 못했다.** Ultra 경로는 7건 중 최초 2건, 수정 후 3건이 표시 가능했다. Claude Code + Sonnet 5는 최초 6건, 수정 후 7건이었다. 진단 정확도 점수가 아니라 공통 출력 계약과 조회 검사 결과다.

Trajectory를 보면 Ultra의 남은 네 실패는 없는 근거를 만든 문제가 아니었다. 원본에 존재하는 사실을 점검 이유가 참조했지만, 수정된 관측 목록에서 그 사실이 빠져 있었다. 사실 목록과 점검의 참조 목록을 모델이 따로 작성하면서 관계가 끊어진 것이다. 다음 구현은 이 중복 작성을 줄이는 방향이 타당하다.

## 비교 조건

- 출력 계약 v2, 같은 질문·자료·코퍼스 해시, 같은 최대 1회 수정 기회.
- 수정은 실패 이유와 이미 읽은 근거만 사용한다. 두 구성 모두 수정 단계에서 새 도구를 사용할 수 없다. 답변을 사람이 잘라내거나 출처를 임의로 붙이지 않았다.
- Ultra 도메인 도구 경로와 Sonnet5의 제한된 파일 조사 경로를 비교했다. 모델과 하네스가 함께 다르므로 하네스만의 인과 효과를 분리한 실험은 아니다.
- 이전에 본 5건은 개발·회귀용. 새 설비의 신고 37/5는 추론 전에 고정한 시간순 선정 규칙으로 선택했다.
- 현재 사건의 사후 진단은 입력과 평가 feedback에 제공하지 않았다. 모두 지역난방 신고이며 발전소 현장 일반화를 뜻하지 않는다.

## Trajectory에서 확인한 원인

### 1. 수정으로 새로운 참조 불일치가 생겼다

사례 52의 최초 응답은 관측 16개를 선택해 최대 12개 조건을 넘겼다. 수정 후에는 12개로 줄었지만, 점검 이유가 사용하는 두 사실은 관측 목록에서 빠졌다. 그 ID들은 실제 조회한 카탈로그에 존재했다. 따라서 이를 ‘없는 근거 생성’으로 계산하면 잘못된 분석이다.

최종 보류된 네 Ultra 응답에서 같은 종류의 선택 불일치가 관측됐다. [최종 단계 audit](audit/trajectory-audit-final.md)은 `known_but_unselected`와 실제 미등록 ID를 구분한다. 최초와 수정 후 상태도 [각각](audit/trajectory-audit-initial.md) 보존했다.

### 2. 참조 검사 통과가 이유 문장의 타당성을 보장하지 않는다

시간 방향, 숫자, 인과 표현에 대한 동일 휴리스틱을 두 구성에 적용했다. 이것은 전문가 정답이나 자동 의미 오류 판정이 아니라 원문 검토 지점이다. 마지막 값 하나로 추세를 표현하거나, 시점이 없는 최소·최대 값을 시간 순서처럼 설명하는 경우를 따로 확인해야 한다.

수정 재시도는 형식 오류에만 반응했다. 이미 형식이 맞는 답변의 점검 이유가 약하다고 추가 기회를 주지 않았다. [가린 응답 쌍](review/blind-review.md)은 내용 검토에 사용할 수 있지만 작성자 검토를 독립 전문가 평가로 부르지 않는다.

## 별도 개발 시험 A — 스키마 제약과 근거 참조 기반 구성

주 비교 조건은 바꾸지 않고 독립적인 `constrained_composer`를 만들었다.

1. 모델은 점검 유형과 이를 뒷받침할 기존 fact ID를 선택한다.
2. 관측 목록은 그 참조의 합집합으로 프로그램이 구성한다. 점검이 가리키는 사실이 표시 목록에서 빠지는 중복 작성 문제를 줄인다.
3. Ultra의 native JSON schema로 허용 ID·배열 크기 등을 제한하고, 중복 등 남은 조건은 로컬에서 거부한다. 출처나 사실을 새로 만들거나 기존 실패 답변을 통과로 재분류하지 않는다.
4. 기존 v2 검증기와 조회 검사를 그대로 적용한다.

세 번의 제한된 개발 요청을 보존했다. 첫 합성 요청은 `uniqueItems` 미지원으로 HTTP400이었고, 해당 native 키를 제거하되 로컬 중복 검사를 유지한 두 번째 합성 요청은 통과했다. 사례52의 이미 조회된 근거를 사용한 세 번째 요청은 관측12개·점검3개로 계약 검사를 통과했다(10.73초, 보고된 prompt8,259/completion434토큰).

**이는 이미 본 사례 한 건의 출력 구성 단계 개발 검증이다.** 전체 조사 루프의 새 사건 평가, Sonnet과의 동등한 비교, 의미적 정확도 증거가 아니다. 최소값57.2°C와 마지막값68.6°C를 ‘상승’으로 서술한 이유는 특히 시점 확인이 필요하다. 기간 처음부터 계속 상승했다는 의미로 읽으면 안 되며, 정확한 시간 순서는 추가 조회해야 한다.

## 별도 개발 시험 B — 시점별 근거 추출

`temporal_evidence`는 공개 원자료에서 공급온도–설정값 편차 구간과 동일 시점의 값을 계산한다. 임계값2°C는 기존 POC의 기술적 설명 기준이며 검증된 설비 보호·고장 기준이 아니다.

사례3에서는 2015-11-30 14:50–15:30의 5개 샘플 구간을 확인했고, 15:00의 공급45.7°C·설정32.0°C가 최대 편차13.7°C를 만든다. 이것은 구간과 시점을 확인한 것이지, 그 편차의 원인이나 고장 여부를 입증한 것이 아니다.

이번 모델 비교에는 이 정보를 추가하지 않았다. 다음에는 시간적 주장을 할 때 해당 구간을 실제로 조회하도록 연결하고, 같은 원자료 접근 조건으로 다시 비교해야 한다.

## 다음 회차의 검증 대상

- 근거 참조에서 관측을 구성하는 방식을 실제 조사 루프에 연결하고, 본 적 없는 사건에서 출력 안정성을 확인한다.
- 시간·수치 관계를 주장할 때 필요한 구간·양끝값·동시 계측을 조회하게 한다. 형식 오류와 의미 오류를 따로 평가한다.
- 같은 근거 접근 조건과 명시된 출력 계약으로 Sonnet을 유지한다. 초기 실패·수정 비용·보류도 성과에 포함한다.
- 새 사례의 결과를 본 뒤 정답·규칙·제한을 바꿔 이번 회차의 승률을 높이지 않는다.

현재 결론은 **재시도보다 출력의 근거 관계를 명시적으로 구성하는 설계가 더 유망하다는 개발 증거를 얻었다**는 것이다. Sonnet 대비 실증 우위는 아직 없다.
