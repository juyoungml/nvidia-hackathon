# Plant Reliability Agent

## 설비 이상 신고가 들어오면, 첫 조사를 대신 해 두는 에이전트

2026 NVIDIA Korea Agentic AI Hackathon · 공개 데이터 기반 POC

NVIDIA 스택: Nemotron 3 Ultra(NIM)가 도구를 고르고 점검안을 쓰며, NeMo Agent Toolkit이 읽기 도구를 실행하고, OpenShell로 읽기 전용 정책을 별도 시험했다([자세히](#사용한-nvidia-기술)).

## 풀고 싶은 문제

발전소나 열공급 설비에 이상 신고가 들어오면, 엔지니어는 먼저 자료를 뒤진다. 이 센서가 정확히 무엇을 재는지, 그 값이 언제 기록된 것인지, 전에 비슷한 신고나 정비가 있었는지. 원인을 추정하기 전에 이 대조 작업에 상당한 시간이 든다.

계측값이 정상처럼 보일 때가 더 어렵다. 공급온도가 설정값을 잘 따라가고 있어도 고객은 난방이 안 된다고 할 수 있다. 계기판에 없는 정보, 예를 들어 실내 온도나 2차측 유량을 확인해야 한다는 판단이 필요하다.

Plant는 이 첫 조사를 맡는다. 신고를 받으면 관련 계측과 이력을 스스로 골라 읽고, **다음에 무엇을 확인해야 하는지, 왜 그런지, 무엇이 아직 빠져 있는지**를 원본 기록과 연결해서 엔지니어에게 넘긴다.

이번 POC는 공개 지역난방 데이터(PreDist v2)로 만들었다. 발전소 현장 적용은 다음 단계다.

## 실제 사례: 신고 52

2016년 12월 12일 15:55, 한 서브스테이션에 난방 불량 신고가 들어왔다. 신고 전 24시간 동안 144개의 계측이 있고, 2차측 공급온도는 설정값과 평균 0.31°C 차이로 잘 맞았다. 계측만 보면 정상이다.

에이전트가 정리한 내용은 다음과 같다.

| 데이터로 확인되는 것 | 데이터로는 모르는 것 | 그래서 다음에 확인할 것 |
|---|---|---|
| 시간대별 2차측 공급온도와 설정값 | 실내·라디에이터의 실제 온도 | 영향받은 공간과 말단 온도 |
| 1차측 네트워크 유량 | 고객 쪽 2차 회로 유량 | 2차측 유량을 측정해 운전 범위와 비교 |
| 설정값이 63.0°C에서 68.6°C로 바뀜 | 자동 제어인지 수동 변경인지 | 제어기 설정·경보·변경 이력 |

원인을 단정하거나 설정을 바꾸라고 지시하지 않는다. 엔지니어가 검토할 점검안이다. 신고 이후의 진단이나 조치 기록은 입력에서 뺐다. 원본은 [PreDist v2](https://zenodo.org/records/19496480), 재생 입력은 [replay-52.json](../data/replay-52.json)에 있다.

## 작동 방식

1. **신고 시점을 기준으로 자료를 준비한다.** 설비, 신고 내용, 접수 시각, 볼 수 있는 계측 구간을 정한다. 그 이후 정보는 넣지 않는다.
2. **Nemotron 3 Ultra가 필요한 자료를 고른다.** 최근 계측, 과거 신고, 정비 이력, 센서 정의, 시간대별 온도·설정값, 편차 구간을 읽는 도구 6종 중에서 선택한다. 계획 단계는 최대 6회다.
3. **점검안을 근거와 함께 낸다.** 모델은 점검 항목, 이유, 참고한 기록 ID를 출력한다. 프로그램이 그 ID를 원본 값에 연결해서, 제안과 근거가 어긋나지 않게 한다.
4. **검사 후 사람에게 넘긴다.** 인용한 기록이 실제로 조회한 것인지, 형식이 맞는지 자동으로 확인한다. 시간이나 수치 설명에 근거가 빠진 것 같으면 경고를 붙인다.

조회 한도를 다 쓰고도 에이전트가 조사를 끝내지 않으면, 그때까지 모은 자료로 정리하게 했다(`bounded_finalize_v2`). 이 경우 "스스로 끝낸 것이 아니라 한도에 도달했다"는 표시를 남긴다. 사례 52에서 이 방식으로 도구 6회 조회 후 27.8초 만에 관측 12개와 점검 3개가 나왔다([실행 기록](../evaluation/cycle4/development/handoff-v2-case52.json)).

## 설비 도메인을 반영한 설계

**측정 위치를 헷갈리지 않게 했다.** 1차측 유량을 2차측 유량으로, 공급온도를 실내 온도로 착각하지 않도록 센서의 의미와 한계를 도구 설명에 넣었다.

**시간을 따로 다룬다.** 최솟값·최댓값과 처음·마지막 값을 구분하고, 같은 시각의 공급온도와 설정값을 짝지어 조회할 수 있다. 결측이나 불규칙한 간격도 그대로 보여준다.

**모든 제안에서 원본으로 돌아갈 수 있다.** 기록 ID마다 출처, 필드, 시각, 값을 담았다. 화면에서 점검 항목을 누르면 그 판단에 쓴 원본 값이 바로 열린다.

## 비교 실험

같은 사건, 같은 자료, 같은 출력 형식으로 Ultra 경로와 Claude Code + Sonnet 5 경로를 비교했다. 사례와 데이터 해시는 실험 전에 고정했다([프로토콜](../evaluation/cycle4/PROTOCOL.md)). Sonnet 쪽은 파일 읽기·검색과 구조화 출력만 쓰게 했다. 모델과 실행 환경이 함께 달라서 어느 쪽 효과인지는 분리되지 않는다.

| 근거 연결 검사 통과 | Ultra | Sonnet 5 |
|---|---:|---:|
| 개발에 쓴 사건 (52, 3) | 1/2 | 2/2 |
| 처음 보는 설비 사건 (29, 47) | 1/2 | 2/2 |
| 합계 | **2/4** | **4/4** |

Ultra가 놓친 2건은 모두 조회 6회를 다 쓰고 나서 조사 종료를 선언하지 못한 경우였다. 앞서 말한 한도 도달 후 정리 방식이 이 문제를 고친 것이다. 수정 결과는 위 표에 넣지 않았다.

둘 다 결과를 낸 2건은 이름을 가리고 별도 AI 검토자에게 점검 내용을 평가받았다. 점수는 Ultra 41/48, Sonnet 42/48로 비슷했고, 양쪽 모두 점검 6개 중 3개에서 중요한 근거가 빠져 있었다([평가 결과](../evaluation/readiness/content-review/v2/CONTENT_RESULTS.md)). 표본이 작아서 우열을 말하기는 어렵다.

실험 중 발견한 문제도 기록해 두었다. 첫 평가 자료에서 점검 본문이 빠진 것을 발견해 다시 평가했고, 요청 로그에 이후 메시지가 섞이는 버그를 고쳤다. 자세한 내용은 [전체 결과](../evaluation/cycle4/RESULTS.md)에 있다.

## 사용한 NVIDIA 기술

이 프로젝트는 범용 챗봇이 아니다. NVIDIA 모델이 실제 도구를 직접 고르고, 그 도구가 돌려준 기록을 근거로 점검안을 쓰는 에이전트 구조다.

| 기술 | 이 프로젝트에서 맡은 일 | 상태 | 확인할 곳 |
|---|---|---|---|
| **Nemotron 3 Ultra** (NVIDIA NIM 호스팅 API, `nvidia/nemotron-3-ultra-550b-a55b`) | 에이전트의 두뇌. 읽기 전용 도구 6종 중 무엇을 부를지 고르고(tool calling), 최대 6번의 계획 요청으로 결과를 비교한 뒤, 최종 점검안을 JSON 스키마 구조화 출력으로 쓴다. 모든 요청·도구 결과·근거 검사를 기록한다. | 모든 데모 실행의 핵심 경로 | [실행 코드](../poc/live_investigation.py), [사례 52 기록](../poc/trace-52-nvidia-nemotron-3-ultra-550b-a55b.json), [구조](../ARCHITECTURE.md) |
| **NeMo Agent Toolkit (NAT) 1.8.0** | 읽기 도구 6종을 등록하고 실행한다. 키 없이 도는 동등성 시험에서 직접 호출과 결과가 같았고, 별도 사례 52 개발 실행에서 모델이 고른 6번의 조회를 NAT가 실행했으며 점검안이 근거 검사를 통과했다. 계획 루프 자체는 우리 Python 코드다. | 연동 완료 (선택 backend `--read-backend nat`) | [NAT 연동](../integrations/NAT_LIVE.md), [동등성 기록](../integrations/nat-live-smoke.json), [사례 52 기록](../integrations/nat-live-case52.json) |
| **OpenShell 0.1.2** | 공개 시험 자료로 정책을 따로 시험했다. 허용된 읽기는 통과하고, 비허용 읽기·쓰기·직접 TCP 연결은 막혔다. 전체 추론 경로에는 아직 적용하지 않았다. | 별도 시험 완료 | [시험 설명](../integrations/openshell-README.md), [정책](../integrations/openshell-policy.yaml), [기록](../integrations/openshell-trace.json) |
| **Nemotron Nano**, **NeMo Retriever** | Nano는 많은 신호를 상시 감시하고 관련 자료를 재정렬하는 역할, Retriever는 문서·도면 검색 역할로 계획했다. 이전 Nano 분류 실험 기록은 남아 있지만 주 경로에는 없다. | 계획 | [구조](../ARCHITECTURE.md), [이전 Nano 실험](../poc/trace-52-ollama-nemotron-3-nano-4b.json) |

API 키와 회사·고객 자료는 제출물에 없다. PreDist는 CC BY 4.0 공개 데이터다. DOE 증기 계통도는 공개 도면 탐색 예시로만 넣었고 PreDist 설비와는 관계가 없다.

## 다음 단계

목표는 엔지니어가 다음 점검을 정할 때 자료를 찾고 대조하는 시간을 줄이는 것이다. 모델 응답 시간은 이 시간을 대신하지 못하므로 따로 측정해야 한다.

다음 실험에서는 같은 신규 사건을 현장 경험자에게 주고, 기존 방식과 Plant를 번갈아 쓰게 한다. 첫 번째 쓸 만한 점검안이 나오기까지의 시간, 빠진 근거, 불필요한 점검, 근거 없는 확신을 함께 본다. 평가자는 어느 방법인지 모르게 한다.

그다음은 발전소 설비로의 확장이다. Nemotron Nano로 수만 개 신호를 상시 감시하다가 이상 징후가 보이면 먼저 조사를 시작하는 구조를 계획하고 있다.

Plant는 설비를 자동으로 제어하지 않고, 현장 운전 절차를 대신하지 않는다. 판단은 엔지니어가 한다.
